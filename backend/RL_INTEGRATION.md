# CleanRoute AI reinforcement-learning integration

## What was found

The supplied `ppo_model.zip` is a Stable-Baselines3 2.9.0 PPO checkpoint with 16,861 recorded training timesteps. Its actor is 48 → 64 → 64 → 14 with Tanh activations; its critic has a separate 48 → 64 → 64 → 1 network. The training contract was checked against `train.ipynb` and `G3_baseline_agents.py` in the supplied G3 folder. The attached Streamlit deployment uses ReLU and permits fills above the trained observation bound; those discrepancies were not copied.

The policy chooses one of six bins or a depot, with direct/alternate route modes. It does not predict sweep angle, overlap, geographic coordinates, or robot commands. CleanRoute AI originally provided deterministic planning, bounded recovery, an independent KPI evaluator, route versioning, approval, and simulated segment execution. These remain the operational pipeline.

## Runtime contract and limitations

RL support is optional: install `python -m pip install -r backend/requirements-rl.txt`. Runtime uses extracted `backend/rl_assets/ppo/policy.pth` and `model.json`; model loading is lazy. The original `ppo_model.zip` remains in Downloads and is not required at runtime. Explicit legacy archive paths remain supported through `CLEANROUTEAI_RL_CHECKPOINT`. Missing dependencies/checkpoints, incompatible schemas, invalid policy outputs, and incomplete mission inputs explicitly use deterministic fallback. `use_rl: false` disables inference for paired baseline runs.

The versioned adapter requires six collection tasks with explicit `rl_bin_state` (`fill_kg`, `traffic_multiplier`, `accident`) and matching operator/simulated weight estimates. Geographic coordinates are projected into a common-scale local grid relative to the depot. This is a documented domain transfer, not a claim that the model was trained on CleanRoute AI maps. Unsupported area-sweep missions and missing bin telemetry fall back. The supplied checkpoint cannot tune sweep settings.

The trained ordering is preserved: vehicle x/y, battery, load, six fills, six bin x, six bin y, six traffic multipliers, six accident flags, six distances, six collected flags, completed collection/depot decision count, depot distance. Original denominators remain 9, 100, 250, 100, 2, sqrt(2)×9, and 200 as applicable. See `rl_policy.py` for the precise encoder and compatibility checks.

Runtime restricts the original action distribution to available direct collection actions. Alternate-road and depot choices are masked because the current mission planner does not expose the G3 environment's alternate-road semantics. The original argmax and permitted selection are recorded. A selected task is a scheduler preference, after collecting the maximum feasible task count and priority total. All paths, windows, payload handling, battery limits, and approvals remain deterministic.

## Feedback loop

1. Existing event handling or the planning API obtains the current mission snapshot. Same-machine replans preserve recorded position, elapsed time, completed work, and machine resources.
2. The deterministic baseline is generated and independently evaluated.
3. A compatible frozen PPO policy recommends a permitted next collection task. Its candidate is generated by the same planner and evaluated by the same KPI gate.
4. CleanRoute AI KPI reward v1 and metric deltas are calculated from evaluator output. A feasible PPO candidate must improve baseline reward by the configured epsilon to replace a passing baseline. Failed hard constraints always reject a proposal, even with a positive reward.
5. Existing iteration/time limits bound generation. Failed candidates remain in feedback; the selected candidate requires approval. Duplicate event and stale-route protection remain in the existing event subsystem.
6. Simulated execution provides recorded progress and current KPI feedback. Runtime inference never calls `learn()` or updates checkpoint weights.

The reward is distinct from the original G3 training reward. Configurable weights live in `RLRewardConfig`: +40 coverage fraction, +25 planned collection assignment fraction, +10 battery fraction, −10 distance/max-distance (capped at 2), −10 duration/max-duration (capped at 2), −5 repeated-coverage fraction, and −25 per hard failure. Collection-only routes use full coverage as a neutral constant. This is a candidate comparison score, not evidence of retraining or a replacement for feasibility gates.

Original G3 training reward is `-(energy + 0.1 * effective_distance)`, plus `80 * timely_bins_serviced / 6` on collection. It has no explicit overflow penalty. No training or fine-tuning was requested or performed. The supplied standalone grid environment is retained in its original folder; it is not presented as an CleanRoute AI training environment. Training a policy on CleanRoute AI planner transitions remains a separate, explicitly invoked future workflow.

## Multi-outing completion and changing daily routes

The Route console now enables **Return to depot, recharge & resume** by default. API callers must explicitly send `enable_depot_cycles: true`; its default is `false` to preserve the existing single-mission contract. This feature schedules feasible work portions, validated return travel, stationary depot service, and transit to the next unfinished segment. It preserves all pending work and the final depot return. Replans retain completed work, position, mission time, current battery, and the time/distance already spent in the current outing.

With the feature enabled, the default **90-minute** duration and **15,000-metre** distance limits apply per outing, together with the **20% minimum battery reserve**, including safe return travel. Total job time and distance are reported without applying those single-outing limits to the whole job. The independent evaluator replays the pending segments rather than trusting forecast summaries, checking continuity, geometric distance, reserve, depot location, service duration, and collection deadlines. The executor also checks that the remaining outing retains enough energy for its depot return before proceeding.

`MachineProfile.depot_service_minutes` defaults to **20 simulated minutes**, and `recharged_battery_percent` defaults to **100%**. Depot visits unload the payload; battery resets only after the stationary service segment completes at the depot, with a `DEPOT_RECHARGE` audit record. Depot time counts toward completion and collection deadlines. A simulation request advances the estimated time without waiting for a real charging cycle. Scheduling is bounded at **32 service stops**; unreachable depot access, an individually infeasible work portion plus return, geometry failures, deadline violations, or the service-stop cap still block execution. Disabling depot cycles restores single-mission limits, where a smaller area may be required.

For area-sweep jobs, the bounded deterministic comparison evaluates sweep alternatives with depot detours and service included, and reports their candidate feedback and total completion estimates. A daily boundary, obstacle, or depot change produces a new evaluated route version. Completion estimates are elapsed mission minutes plus remaining work/service time, not a wall-clock appointment or a promise of physical performance.

The server saves selected feasible depot-cycle planning summaries to `backend/runtime/mission_history.json`, which is ignored by Git. Completion callbacks add the actual **simulated** mission elapsed time while preserving the original estimate. These records survive restart and are exposed through `GET /api/feedback/history` (optional `machine_id` filter). A matching workload fingerprint can place its fastest previously feasible sweep angle first in the next candidate search. That setting is reevaluated and receives no exemption from current geometry or KPI gates. The fingerprint includes start/depot, area, obstacle geometry, tasks and windows, machine resources/capabilities, terrain, and policy; random generated IDs do not make an otherwise identical workload different. Changed daily conditions receive their own comparison group. Corrupted files or invalid records are reported in the API detail; valid records are retained when possible.

This local summary history is a deterministic warm start, not an update of the PPO or proof of improvement on a different workload. It does not store the complete state/action/next-state transitions needed for policy training. Active routes, progress and telemetry remain in memory, so history cannot restore a paused mission after restart.

The supplied frozen PPO remains a **six-bin collection dispatch policy**. It cannot recommend area-sweep patterns, learn new daily map layouts, or train itself from these comparisons. Its depot actions remain masked in the G3 adapter; deterministic depot scheduling is a separate operational feature. No `learn()` call, online weight update, persistent training dataset, or area-sweep/depot training environment has been added. Feedback and logs make the current planner decisions inspectable. A learning-based daily improvement workflow requires a compatible state/action/reward contract, recorded execution transitions, offline training, and evaluation against the deterministic baseline before deployment.

## UI and API

The sidebar now has **Feedback** and **Logs & changes**. Feedback shows checkpoint availability versus mission compatibility, original action/selected task, candidate sources, KPI failures, reward components and deltas, and simulated execution feedback. Logs use the existing audit log and route-version history. Values come from backend records.

For depot-cycle missions, both Route and Feedback also display the whole-job completion estimate, outing count, recharge stops, service time, longest outing, and minimum battery. These are planned or simulated quantities with their existing provenance; repeated daily use does not make them measured real-world results.

- `GET /api/rl/status`: checkpoint/inference status.
- `GET /api/routes/{route_id}/feedback`: candidate traces and simulated execution feedback.
- `GET /api/feedback/history?machine_id=...`: locally saved feasible depot-cycle plans and simulated completion summaries, with storage-status detail. The machine filter is optional.
- `POST /api/rl/demo` with `{ "use_rl": true, "seed": 42 }`: controlled six-bin simulation through the same operational planner; does not approve or execute it.
- Existing `/api/routes/plan`, events, approval, and execute/resume endpoints remain the mission interfaces.

## Repeatable demonstration

1. Start backend/frontend, open **Feedback**, and run **six-bin RL demo**. The demo supplies explicitly simulated bin mass, traffic and accident inputs.
2. Inspect the deterministic baseline and PPO candidate, their hard-constraint results, differences, reward, and final selection. Run the baseline demo to inspect equivalent inputs without policy inference.
3. On an operational mission, enable **Return to depot, recharge & resume**, select an area large enough to need more than one outing, and review the service stops and total completion time. Add a validated obstacle or collection task, or move the depot. Replanning uses existing mission state and compares the changed feasible schedule. Incompatible bin observations produce a clear fallback explanation instead of an invented RL action.
4. Approve an eligible route in Route view, run the simulator, then inspect recorded execution feedback and logs. The demo preview itself does not execute a route.

## Verification and measured results

Multi-outing validation on 2026-10-23: **122 backend tests passed**, including original-versus-extracted PPO equivalence using the reference archive in Downloads, real YOLO CPU inference from `vision_assets/best.pt`, depot service/resume, obstacle replanning, lifetime service limits, completion-time selection, and saved history. **20 frontend tests passed** and the TypeScript/Vite production build passed.

A 38,416 m² clear simulated site produced six feasible alternatives. The selected six-outing/five-service schedule estimated 566.15 minutes including service, versus 569.45 minutes for the first candidate. A separate campus-terrain scenario passed with no route safety issues, six outings/five services, 579.84 minutes total and a longest outing of 89.64 minutes; planning took 16.8 seconds. These are deterministic planning/simulation checks, not PPO training results or proof of a global optimum.

The optional archive-equivalence test can be enabled with `CLEANROUTEAI_RL_REFERENCE_ARCHIVE` pointing to the original PPO ZIP. Runtime uses the extracted model and does not need that ZIP inside the backend.

The counts and paired PPO results below record the earlier six-bin integration validation. They are not a measurement of the newer multi-outing feature or evidence of daily learning. Its focused verification command is:

Remaining scope: no online learning/fine-tuning, no learned sweep control, no traffic inference from map images, no G3 alternate-route/depot action execution, no model persistence beyond the supplied checkpoint, and no physical actuation. To use RL for a different observation/action space or actual road-dispatch domain, train/evaluate a compatible policy through an explicitly authorized workflow.
